# ADR-0004：使用书库 sidecar JSONL 变更流同步应用数据

- 状态：已接受
- 决策日期：2026-05-03
- 记录日期：2026-07-22
- 记录方式：根据 Git 历史和现存实现回溯补录
- 部分取代：[ADR-0003](./0003-myreader-sync-technology-selection.md) 的 CR-SQLite、Manifest/CAS 数据库同步方案
- 后续决策：[ADR-0012](./0012-mobile-sync-refactor.md)、[ADR-0014](./0014-data-ownership-and-sync-storage.md)

## 说明

这项决策在实施时没有单独的 ADR。本文根据 2026-05-03 起的提交、桌面和移动端现存同步
实现，以及后续书库路径和同步入口重构回溯补录。

本文记录的是**书库域现行同步协议的架构边界**，不是未来用户域 `profile-v1` 协议。两者可以
使用相似的按设备变更段布局，但必须独立版本化。

## 背景

[ADR-0003](./0003-myreader-sync-technology-selection.md) 原计划通过 CR-SQLite CRR 表、
`crsql_changes`、Manifest/CAS 和可加载 SQLite 扩展同步 MyReader 数据。实施过程中出现了
几个更基础的问题：

- 桌面和移动使用不同 SQLite 运行时，原生扩展的构建、签名、打包和升级路径不同。
- MyReader 当时需要同步的核心数据主要是阅读进度，数据量小、主键和冲突规则明确。
- 每个 Calibre 书库已经有独立存储边界，没有必要把本机生成的 `library_id` 写入跨设备主键。
- WebDAV、OneDrive 和本地共享目录只保证文件或对象操作，不提供在线数据库事务。
- 同步数据需要可检查、可恢复，并能够在不打开远端 SQLite 的情况下逐段应用。

2026-05-03 的 `cca40722` 首次落地 per-library 阅读进度数据库和 JSONL LWW 同步；同日
`596fbc75` 删除同步主键中的 `library_id`，因为数据库文件路径已经限定书库，而不同设备会
为同一书库生成不同本机 ID。

## 决策驱动因素

1. 保持 local-first，远端不可用时本地数据库仍可完整读写。
2. 不让多个设备直接打开或覆盖同一个远端 SQLite 文件。
3. 同一协议能够运行在桌面 Rust、移动 TypeScript 和不同对象存储后端上。
4. 变更文件应可检查、可重放，并允许按远端设备独立恢复进度。
5. 同步身份不能依赖本机书库注册 ID。
6. 不为了尚未出现的复杂冲突引入原生 CRDT 扩展和跨平台构建成本。
7. 删除必须可以传播，不能因为本地物理删除而在另一设备复活。

## 考虑过的方案

| 方案 | 优点 | 主要问题 |
|---|---|---|
| 直接同步 `myreader.db` | 实现表面简单 | 云盘并发覆盖、WAL 和锁语义不可靠，无法合并离线写入 |
| CR-SQLite 变更集 | 字段级 CRDT 合并能力强 | 两套原生 SQLite 运行时都要可靠加载扩展，构建与迁移成本高于当前数据需求 |
| 单个共享 JSON 快照 | 容易查看 | 每次都要读改写整个快照，并发写入仍会覆盖 |
| 中心服务器数据库 | 可提供事务和统一身份 | 引入账户、服务可用性和运维依赖，不符合当前存储后端范围 |
| 按设备追加 JSONL 变更段 | 无共享写热点，适配文件后端，容易重放 | 需要应用自行维护游标、幂等、冲突和压缩策略 |

## 决策

书库域继续在每台设备使用本地 SQLite 作为查询和事务数据库；跨设备只传输应用自有的逻辑
记录，不传输活动 SQLite 文件。

### 存储边界

每个 Calibre 书库拥有自己的 sidecar：

```text
<calibre-library>/
└── .myreader/
    ├── myreader.db
    └── changes/
        ├── <device-a>/
        │   ├── <sequence>.jsonl
        │   └── ...
        └── <device-b>/
            └── <sequence>.jsonl
```

远程书库可以在设备私有目录中维护本地镜像，但对外交换的逻辑路径仍是该书库根下的
`.myreader/changes/`。

数据库文件所在书库就是同步作用域。因此，业务主键只包含书库内稳定字段，例如阅读进度使用
`book_id + format`；不得加入每台设备各自生成的 `library_id`。

### 变更段

- 每个设备只写自己的 `changes/<device_id>/` 目录，避免多个设备覆盖同一个对象。
- 文件名使用该设备单调递增的本地序号；一个文件包含一条或多条 JSONL 记录。
- 每一行描述表名、业务主键和值，不包含数据库页、SQL 事务日志或 ORM 私有结构。
- 写入远端成功后才能推进本地推送游标。
- 拉取按远端设备分别维护已连续处理的序号；成功读取并处理文件后才能推进该设备游标。
- 重复读取同一变更不得造成重复实体或累计型副作用。

### 表和冲突规则

同步表必须通过显式规格注册，声明：

- 表名；
- 业务主键字段；
- 可同步值字段；
- 冲突比较字段；
- 删除和 tombstone 规则。

当前默认实现使用记录级 `updated_at` LWW，适合单用户多设备下的阅读位置和实体状态。书签、
批注等可删除实体必须保存 tombstone，并将删除时间纳入合并。

LWW 不是所有未来数据的默认答案。阅读事件、完成历史等不可约事实应使用稳定事件 ID 求并集，
并由 [ADR-0014](./0014-data-ownership-and-sync-storage.md) 所定义的用户域协议负责。

### 传输与业务分离

同步引擎只依赖列举、读取和写入对象等存储能力。WebDAV、OneDrive 和本地共享目录负责传输，
不决定业务主键或冲突规则。UI 也不得直接读写变更段，而应调用书库同步入口。

CR-SQLite 可以在未来作为某个 `SyncProvider` 的实现重新评估，但不能改变既有远端格式或业务
语义而不增加协议版本和迁移方案。

## 结果

### 正面结果

- 本地 SQLite 与远端文件存储职责分离，离线读写不依赖云端。
- 不同设备没有共享写热点，WebDAV 和 OneDrive 都能承载相同逻辑协议。
- 变更文件可检查、可备份、可按设备重放。
- 书库数据随 sidecar 移动，删除应用内书库注册不会删除原始记录。
- 新同步表可以逐项声明主键和合并规则，不绑定特定 ORM。

### 代价和风险

- 当前增量枚举仍依赖 `updated_at` 和同时间戳指纹集合，墙上时钟回拨需要额外防护。
- 变更段会持续增长，当前没有压缩快照和安全垃圾回收协议。
- JSONL 记录缺少统一的显式协议 envelope；破坏兼容的字段变化必须谨慎处理。
- 记录级 LWW 可能丢失同一实体的并发字段修改，不适合追加型事件。
- 设备身份丢失或本地 sequence 回退时必须检测冲突，不能覆盖既有远端文件。

## 长期约束

1. 多台设备不得直接把远端 `myreader.db` 当作在线数据库打开。
2. 每个设备只写自己的变更目录；已发布的变更段不得静默覆盖。
3. 同步记录不得使用本机 `library_id` 作为跨设备身份。
4. 游标只有在对应变更段被成功处理后才能推进。
5. 新增同步表前必须明确主键、冲突、删除、幂等和版本兼容规则。
6. 追加型事件不得用记录级 LWW 或累加聚合值替代稳定事件身份。
7. 未知记录类型或不支持的协议版本不得静默确认并推进游标。

## 取代本决策

如果未来书库域改用中心服务器作为唯一权威、采用新的 CRDT 线协议，或者取消书库 sidecar，
必须新增 ADR，说明远端历史迁移、离线行为、旧客户端兼容和用户导出路径。
