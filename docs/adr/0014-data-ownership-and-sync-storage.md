# ADR-0014：将应用数据拆分为书库域和用户域

- 状态：已撤回（未实施）
- 日期：2026-07-22
- 决策范围：桌面端、移动端、共享数据库、同步协议
- 当前书库域同步：[ADR-0004](./0004-library-sidecar-jsonl-sync.md)
- 后续决策：[ADR-0015](./0015-library-sidecar-crdt-reading-sync.md)

## 撤回说明

本文曾提议让进度、书签和批注继续以书库 sidecar 为同步权威，只把跨书库阅读事件、目标和
设置放入用户域。该方案从未被正式接受或实施，不能作为当前实现依据。

评审随后发现，本文把跨书库统计、未挂载书库历史与本次阅读数据同步绑定在了一起，因此引入了
尚无当前产品需求的中央 Profile、额外同步目录和跨书库身份。MyReader 的多个书库可以分别来自
WebDAV、OneDrive 或本地目录，书库本身已经提供同步目标、访问权限和生命周期；再配置中央目录
会形成重复入口，并让独立书库依赖第三个存储位置。

后续 ADR-0015 因此不接受本文的中央用户域前提：六类现有阅读数据继续由各书库 sidecar 拥有，
协议在书库内升级；跨书库统计另行决策。阅读偏好和应用设置继续仅保存在设备本地。

本文以下正文按最初提案保留，用于记录被撤回方案的背景和权衡。

## 背景

MyReader 当前以 Calibre 书库为数据边界。每个书库在自己的 `.myreader/`
目录中保存应用数据库和同步变更，因此阅读进度、书签等数据可以跟随书库移动、备份，
从应用中移除书库也不会删除书库目录中的数据。

这个边界不适合所有应用数据：

- 阅读时长、连续阅读、年度热力图和已读本数需要聚合全部书库。
- 阅读目标、全局设置、设备注册和同步游标属于用户，而不属于任意一个书库。
- 如果继续把所有数据放在书库中，全局查询必须逐个打开当前可访问的书库；已经移除、
  暂时离线或尚未挂载的书库无法参与统计。
- 如果把所有数据迁到中心目录，进度、书签和批注将不再自然地随书库移动和备份。
- 多台设备不能把云盘中的同一个 SQLite 文件当作在线数据库直接读写。

因此，本决策必须同时确定数据所有权、物理存放位置、稳定身份和同步边界，而不只是为
阅读统计增加一张新表。

## 决策驱动因素

1. 保持 local-first：设备离线时可完整读取和写入本地数据。
2. 书籍归属数据应随书库移动、备份和恢复。
3. 用户全局数据应能脱离任意单个书库存在并聚合全部书库。
4. 从应用中移除书库不得隐式删除书库数据或历史阅读记录。
5. 多端同步必须幂等、可恢复，并允许不同数据使用不同合并算法。
6. 同步后端可以是 WebDAV、OneDrive 或未来的中心服务，但业务层不能依赖某个传输实现。
7. 不同步能够从原始记录重新计算的统计结果。
8. 保持现有书库 sidecar 数据的向后兼容和可迁移性。

## 社区方案依据

- [KOReader](https://koreader.rocks/user_guide/?pubDate=20260514) 默认把书籍进度、
  批注和设置放在书旁边的 `.sdr`，同时也提供中心化、按文件哈希组织的元数据目录；
  阅读统计则集中保存在应用设置目录的 SQLite 数据库中。
- [Readest 的文件同步布局](https://github.com/readest/readest/blob/main/apps/readest-app/src/services/sync/file/layout.ts)
  使用中心根目录、共享索引和按稳定哈希划分的单书配置；其
  [统计同步设计](https://github.com/readest/readest/blob/main/apps/readest-app/docs/superpowers/specs/2026-06-15-koreader-stats-sync-design.md)
  同步不可约的阅读事件，按需计算连续阅读、热力图等派生结果。
- [Komga](https://komga.org/docs/guides/read-progress/) 和
  [Kavita](https://wiki.kavitareader.com/guides/3rdparty/koreader/) 展示了中心服务作为
  用户进度权威来源的方案；这种方案多端一致性强，但数据生命周期依赖服务器和用户账户。
- [Readium Navigator](https://readium.org/swift-toolkit/3.8.0/documentation/readium/navigator/)
  要求应用保存并恢复 `Locator`，但不规定数据库位置、表结构或同步算法。
- [SQLite 官方文档](https://www.sqlite.org/useovernet.html) 不建议多个系统通过网络文件系统
  直接共享一个活动数据库文件。

这些方案共同表明，数据应按所有权和生命周期拆分，而不是强迫所有数据使用同一个位置。

## 考虑过的方案

| 方案 | 数据随书库 | 全局查询 | 多端同步 | 主要问题 |
|---|---|---|---|---|
| 全部放书库 sidecar | 优秀 | 差 | 中等 | 必须遍历所有书库，离线书库无法参与聚合 |
| 全部放中心目录 | 差 | 优秀 | 良好 | 书签、进度和批注不再自然随书库移动 |
| 多端直接共享一个 SQLite | 差 | 优秀 | 危险 | 文件锁、WAL、覆盖和云盘冲突无法可靠合并 |
| 书库域与用户域混合 | 优秀 | 优秀 | 良好 | 需要明确身份、作用域和同步协调器 |
| 中心服务器为唯一权威 | 一般 | 优秀 | 优秀 | 引入账户、服务可用性和运维依赖 |

## 决策

采用“书库域 + 用户域 + 设备本地域”的三类数据归属，其中前两类参与同步。

### 书库域

书库域描述某个 Calibre 书库中的书籍状态，继续保存在：

```text
<calibre-library>/.myreader/myreader.db
```

书库域包括：

- 当前阅读位置和 Readium `Locator`
- 阅读进度
- 书签
- 高亮、批注和笔记
- 每本书的阅读格式及个性化设置
- 其他只在该书库内有意义的书籍状态

书库域数据通过该书库自己的同步后端和 `.myreader` 变更流同步。

### 用户域

用户域描述用户跨书库的行为和偏好，保存在每台设备的应用私有目录：

```text
<app-data>/profiles/<profile_id>/profile.db
```

用户域包括：

- 原始阅读时段或阅读事件
- 完成和重读历史
- 阅读目标
- 全局阅读设置
- 跨书库收藏和智能书架
- 已注册书库的稳定引用
- 全应用设备身份、同步游标和同步状态

如果用户配置了中心同步位置，用户域通过独立的 Profile 同步协议复制到该位置。中心位置
保存逻辑记录、不可变变更段和未来的压缩快照，不保存供多台设备直接打开的活动 SQLite。

### 设备本地域

能够安全重建、只对当前设备有意义的数据不参与同步，例如：

- 缩略图和封面缓存
- 搜索索引
- 临时下载状态
- 渲染缓存和性能诊断数据

### 派生数据

下列数据由用户域的原始阅读事件计算，可以在本地缓存，但不是同步权威数据：

- 累计阅读时长
- 连续阅读天数
- 年度热力图
- 每日、每周和每月汇总
- 已读本数

同步派生总数会造成重复累计、口径漂移和难以修复的冲突，因此禁止将其作为同步源。

## 稳定身份

跨设备协议不得使用本机数据库的自增 ID 或本地随机 `Library.id` 作为同步身份。

| 身份 | 含义 | 来源 |
|---|---|---|
| `profile_id` | 一个用户数据空间 | 创建 Profile 时生成，并写入同步清单 |
| `device_id` | 一次应用安装 | 应用私有 Profile 元数据，全应用共享 |
| `library_uuid` | 一个 Calibre 书库 | Calibre `library_id.uuid` |
| `book_uuid` | 书库中的一本书 | Calibre `books.uuid` |
| `book_ref` | 稳定书籍引用 | `library_uuid + book_uuid` |
| `event_id` | 一个不可约用户事件 | 创建事件时生成的 UUID |

内容哈希只能作为缺少 UUID 时的回退或跨书库去重提示，不能替代 `book_ref`。修改书籍文件
可能改变哈希，而复制一个 Calibre 书库应继续表示同一个书库副本。

## 同步入口

产品层只暴露一个统一同步入口，内部由协调器按作用域分发：

```text
syncAll
├── syncProfile
├── syncLibrary(library_uuid: A)
├── syncLibrary(library_uuid: B)
└── refreshDerivedData
```

同步协调器负责调度，不负责统一所有数据的冲突算法。每个同步域必须显式声明：

- 作用域和协议版本
- 稳定主键
- 本地变更枚举方式
- 远端记录格式
- 合并规则
- 删除和 tombstone 规则
- 游标推进条件

## 合并原则

| 数据 | 合并原则 |
|---|---|
| 当前进度 | HLC/LWW，并以 `device_id` 进行确定性决胜 |
| 书签、批注、笔记 | 稳定实体 UUID、字段级 LWW、删除 tombstone |
| 阅读事件 | 按 `event_id` 求并集；重复刷新同一事件时取最大时长，禁止求和 |
| 完成和重读历史 | append-only event；显式删除使用 tombstone |
| 全局设置 | 每字段 HLC/LWW |
| 派生统计 | 不同步，应用原始事件后重新计算 |

所有远端变更必须幂等应用。遇到不支持的协议版本或同步域时，客户端不得静默跳过后推进
游标，否则升级客户端后也无法重新读取被跳过的数据。

## 删除语义

- “从应用中移除书库”只删除本机注册关系，不删除书库 sidecar，不删除用户域阅读历史。
- “删除书库文件”属于存储提供方操作，MyReader 不据此自动清理用户历史。
- “忘记该书库的数据”是独立、显式的破坏性操作，必须向用户说明会产生同步 tombstone。
- “删除 Profile”与“移除书库”是两个不同操作。
- 已移除或离线书库的历史事件仍可参与全局统计，但跳转到书籍前必须重新连接书库。

## 结果

### 正面结果

- 保留书库 sidecar 的可携带性和用户可控性。
- 全局统计不再依赖逐个打开当前可用书库。
- 用户删除或暂时断开书库后，阅读历史仍然存在。
- 各类数据可以选择适合自己的合并算法。
- 未来可以增加中心服务同步后端，而不改变本地数据所有权。

### 代价

- 必须维护 Profile 数据库和统一同步协调器。
- 书库注册、书库内容和用户历史之间需要稳定引用及缺失状态。
- 旧阅读统计必须从本地 `book_id` 迁移到 `book_ref`。
- 用户需要理解“移除书库”和“删除阅读数据”的区别。
- 多个同步域需要独立版本化和兼容性测试。

## 迁移顺序

1. 引入应用级 `profile_id` 和 `device_id`，读取 Calibre `library_uuid`、`book_uuid`。
2. 新建 Profile 数据库，但暂时保留现有书库数据库结构。
3. 以确定性事件 ID 将各书库的旧阅读统计幂等迁移到 Profile。
4. 引入独立的 `profile-v1` 变更流，不向现有书库 v3 流注入新记录类型。
5. 新增统一同步协调器，保留现有书库同步引擎。
6. 逐步迁移阅读目标、全局设置和跨书库组织数据。
7. 数据和运行时验证完成后，再移除旧统计读取路径。

## 必须长期成立的不变量

1. 任意同步记录重复应用都不会重复累计阅读时长。
2. 从应用中移除书库不会删除用户历史。
3. 多台设备不会直接打开同一个远端 SQLite 文件。
4. 同步记录不依赖本机自增 ID。
5. 派生统计不作为同步权威数据。
6. 未知协议版本不会被静默确认或推进游标。
7. 传输后端中不写入访问令牌、密码或其他密钥。

## 取代本决策

如果未来采用中心服务器作为唯一权威来源，或者取消 Calibre 书库 sidecar，需要新增 ADR，
明确数据迁移、离线能力、可导出性和服务不可用时的行为，并将本 ADR 标记为“已取代”。
